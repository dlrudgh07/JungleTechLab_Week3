# 01. 엔진 개요와 설계 철학

## 1. 이 엔진은 무엇인가

한 문장으로: **DirectX 11 위에서 도는, 언리얼 스타일의 구조를 가진 3D 씬 에디터**입니다.

실행하면 하나의 Win32 창이 뜨고, 그 안이 이렇게 나뉩니다.

```
┌──────────────┬─────────────────────────────────────┐
│ Control Panel│                                     │
│  (스폰/씬/    │                                     │
│   카메라/기즈모)│         3D 뷰포트                   │
├──────────────┤        (DirectX 11 렌더링)           │
│ Property     │                                     │
│  (선택 액터의  │                                     │
│   트랜스폼)    │                                     │
├──────────────┼─────────────────────────────────────┤
│ Object List  │         Console (로그)               │
└──────────────┴─────────────────────────────────────┘
```

할 수 있는 일:

- 구/큐브/삼각형/원 등 프리미티브 액터를 스폰하고 배치
- 마우스로 물체를 클릭해 선택 (레이캐스트 피킹)
- 기즈모로 이동 / 회전 / 스케일 조작
- 카메라 자유 이동(WASD + 마우스), 원근 ↔ 직교 투영을 **부드럽게 전환**
- 씬을 JSON으로 저장 / 불러오기
- 와이어프레임, 월드 축 표시, 선택 물체 외곽선 하이라이트
- 실시간 FPS / 메모리 할당량 확인, 콘솔 로그

## 2. 설계 철학 — 왜 이렇게 만들었는가

이 프로젝트의 목표는 "빠르게 동작하는 게임"이 아니라 **"엔진이 내부에서 무슨 일을 하는지 직접 만들어 보며 이해하는 것"** 이었습니다.
그래서 아래 다섯 가지 원칙이 코드 전반에 일관되게 깔려 있습니다.

### 원칙 1. 언리얼의 구조를 그대로 따라간다 (개념 학습 우선)

클래스 이름, 접두사 규칙, 계층 구조가 언리얼 엔진과 의도적으로 동일합니다.

| 이 엔진 | 언리얼 대응 | 역할 |
|---|---|---|
| `UObject` | `UObject` | 모든 엔진 객체의 최상위. UUID / 런타임 타입 정보 보유 |
| `AActor` | `AActor` | 월드에 배치되는 단위. 컴포넌트의 컨테이너 |
| `UActorComponent` | `UActorComponent` | 액터에 붙는 기능 조각 |
| `USceneComponent` | `USceneComponent` | 트랜스폼(위치/회전/스케일)을 가진 컴포넌트 |
| `UPrimitiveComponent` | `UPrimitiveComponent` | 그려지는 컴포넌트 |
| `UWorld` | `UWorld` | 액터들의 소유자 |
| `TArray`, `TMap`, `TSet`, `TQueue`, `TSparseArray` | 동일 | 자체 컨테이너 |
| `FString`, `FVector`, `FRotator`, `FMatrix`, `FTransform` | 동일 | 자체 수학/문자열 타입 |
| `FEngineLoop`, `FEditorViewportClient` | 동일 | 엔진 루프, 에디터 뷰포트 |

접두사 규칙도 언리얼과 같습니다.
- `U...` : `UObject` 파생 클래스
- `A...` : `AActor` 파생 클래스
- `F...` : 일반 구조체 / 매니저 (UObject가 아님)
- `T...` : 템플릿 컨테이너
- `E...` : 열거형

> **발표 포인트**: 언리얼을 써 본 사람은 파일을 열자마자 어디에 무엇이 있는지 짐작할 수 있습니다.
> 반대로 이 엔진을 이해하면 언리얼 소스를 읽을 때의 진입장벽이 낮아집니다.

### 원칙 2. STL은 쓰되, 감싸서 쓴다

`TArray`는 내부적으로 `std::vector`, `TMap`은 `std::unordered_map`, `FString`은 `std::string`입니다.
바퀴를 처음부터 다시 만들지는 않았지만, **인터페이스는 언리얼 스타일로 직접 정의**했습니다.

```cpp
template<typename T>
class TArray
{
public:
    uint32 Add(const T& data);
    void   RemoveAtSwap(uint32 index);
    int32  Num() const;
    // ...
private:
    std::vector<T> mDatas;   // 구현은 STL에 위임
};
```

이유:
1. **학습 목적**: `Add` / `Num` / `RemoveAtSwap` 같은 API가 왜 그런 형태인지 직접 정의하며 이해
2. **교체 가능성**: 나중에 커스텀 얼로케이터로 내부를 바꿔도 사용처는 그대로
3. **의존성 차단**: 엔진 코드가 STL 시그니처에 직접 묶이지 않음

예외가 하나 있습니다. `TSparseArray`는 STL에 대응물이 없어서 **직접 구현**했습니다 (원칙 3 참고).

### 원칙 3. 객체는 "인덱스"로 식별한다 — TSparseArray와 GUObjectArray

모든 `UObject`는 생성되는 순간 전역 배열 `UObject::GUObjectArray`에 자기 자신을 등록합니다.

```cpp
UObject::UObject()
{
    InternalIndex = GUObjectArray.Add(this);   // 전역 등록
    GUObjectRevision++;
}
```

이때 쓰이는 `TSparseArray`가 이 엔진의 핵심 자료구조입니다.

- 원소를 지워도 **뒤 원소가 앞으로 당겨지지 않습니다** (인덱스 안정성)
- 빈 자리는 `union { T Element; int32 NextFreeIndex; }` 슬롯으로 **free-list**를 이루어, 다음 `Add`가 그 자리를 재사용합니다
- 순회는 이터레이터가 빈 슬롯을 건너뜁니다 (`SkipEmpty`)

왜 이게 필요한가? **렌더링과 마우스 피킹을 잇기 위해서**입니다.
GPU에 넘기는 렌더 정보(`FRenderInfo`)에는 포인터 대신 `FObjectID { UUID, InternalIndex }`만 담고,
클릭이 발생하면 인덱스로 O(1) 역참조합니다.

```cpp
uint32 clickedObjectIndex = mHoveredRenderInfo.ObejctID.InternalIndex;
UObject* ClickedObject = UObject::GetObjectByInternalIndex(clickedObjectIndex);
```

`GUObjectRevision`(생성/소멸 시 증가하는 카운터)도 같은 맥락입니다.
ImGui의 오브젝트 목록은 매 프레임 정렬하지 않고, **리비전이 바뀐 프레임에만** 목록을 다시 만듭니다.

### 원칙 4. 리플렉션은 매크로 한 줄로 — REFLECT_CLASS

C++에는 런타임 타입 정보가 빈약합니다. 언리얼은 UHT(코드 생성기)로 해결하지만,
이 엔진은 **매크로 한 줄**로 최소한의 리플렉션을 만듭니다.

```cpp
class AActor : public UObject
{
    REFLECT_CLASS(AActor, UObject)   // 이 한 줄이 전부
    // ...
};
```

매크로가 펼쳐지면 클래스마다 정적 `FClassInfo`가 하나 생깁니다.

```cpp
struct FClassInfo
{
    FString Name;                          // "AActor"
    const FClassInfo* SuperClass;          // UObject::GetClass()
    std::function<UObject*()> Constructor; // new AActor()
};
```

이 세 가지 정보만으로 다음이 전부 가능해집니다.

| 기능 | 구현 |
|---|---|
| `IsA<T>()` | `SuperClass` 체인을 타고 올라가며 비교 |
| `Cast<T>()` | `IsA` 통과 시 `static_cast` |
| 이름 → 객체 생성 | `"UCubeComponent"` 문자열로 `FClassInfo`를 찾아 `Constructor()` 호출 |
| 역직렬화 | JSON의 `"ClassName"` 필드를 읽어 위 방법으로 복원 |

> **발표 포인트**: "리플렉션 없이 JSON에서 클래스를 어떻게 되살리나?"에 대한 답이 이 매크로입니다.
> 단, 이름→클래스 매핑 테이블(`FObjectFactory::mClassInfoMap`)은 아직 **수동 등록**입니다 (코드에도 TODO로 남아 있음).

### 원칙 5. 렌더링과 피킹은 같은 수학을 쓴다

이 엔진에서 가장 공들인 부분이자 가장 특징적인 부분입니다.

보통 엔진은 원근 투영과 직교 투영을 별개의 행렬로 다룹니다. 그러면 두 가지 문제가 생깁니다.
1. 전환할 때 화면이 순간적으로 튄다
2. 화면에 그리는 행렬과 마우스 광선을 만드는 행렬이 따로 놀아, 보이는 것과 클릭되는 것이 어긋난다

그래서 **하나의 파라미터 `t`(perspectiveRatio, 0=직교 / 1=원근)로 두 투영을 연속적으로 잇는 통합 투영 행렬**을 정의했습니다.

```cpp
// Camera.h
FMatrix GetUnifiedProjectionMatrix(float aspect, float fovDegree, float d, float n, float f, float t) const
{
    const float sy = 1.0f / tanf((fovDegree / 2) * PI / 180);
    const float sx = sy / aspect;
    const float A  = ((1.0f - t) + t * f / d) / (f - n);

    FMatrix result = FMatrix::Zero;
    result.M[0][0] = sx / d;
    result.M[1][1] = sy / d;
    result.M[2][2] = A;
    result.M[2][3] = t / d;        // t=0 이면 0 → w가 상수 → 직교
    result.M[3][2] = -n * A;
    result.M[3][3] = 1.0f - t;     // t=1 이면 0 → 완전한 원근
    return result;
}
```

- `t = 1` → 표준 원근 투영 행렬과 동일
- `t = 0` → 직교 투영 행렬과 동일
- `0 < t < 1` → 그 사이의 연속적인 중간 상태

체크박스를 누르면 `t`가 1초 동안 smoothstep으로 보간되며 화면이 부드럽게 넘어갑니다
(`FGraphicsManager::UpdateProjectionTransition`).

그리고 **마우스 피킹은 이 행렬의 역행렬(`GetInverseUnifiedProjectionMatrix`)을 그대로 씁니다.**
그리는 행렬과 클릭 판정 행렬이 수학적으로 같은 식이므로, 전환 도중에도 보이는 대로 클릭됩니다.

> **발표 포인트**: 이 엔진의 "우리 팀만의 것"을 하나만 꼽으라면 이 통합 투영 행렬입니다.

## 3. 명시적으로 하지 않은 것들 (Non-goals)

솔직하게 밝히는 편이 이후 팀 작업에 도움이 됩니다.

| 하지 않은 것 | 이유 / 현재 상태 |
|---|---|
| 멀티스레딩 | `Tick()` 안에 `//Input Threads`, `//Physics Threads`, `//Game Threads`, `//Render Threads` 주석 블록만 있고 실제로는 전부 싱글 스레드. 나중에 분리할 자리를 미리 표시해 둔 것 |
| 물리 / 충돌 | `//Physics Threads` 블록은 비어 있음. 레이-삼각형 교차(피킹)만 구현됨 |
| 머티리얼 / 텍스처 / 라이팅 | 셰이더는 정점 색 + Tint 보간이 전부 (`ShaderW0.hlsl`). 조명 계산 없음 |
| 메시 로딩 | 모든 메시가 헤더 파일에 정점 배열로 하드코딩 (`Sphere.h` 2400줄, `Circle.h` 980줄 등) |
| 컴포넌트 어태치 계층 | `AActor`가 `mRootComponent` + 평평한 `mComponents` 배열을 가짐. 부모-자식 트랜스폼 합성은 미구현 → 모든 트랜스폼이 사실상 월드 좌표 |
| 게임플레이 Tick | 액터가 게임 로직을 돌리지 않음. `Update()`는 렌더 정보를 모으는 용도 (에디터 전용 엔진) |
| 인덱스 버퍼 | 정점 버퍼만 사용 (`D3D11_PRIMITIVE_TOPOLOGY_TRIANGLELIST`) |

이 목록이 곧 **Week3에서 확장할 후보 목록**이기도 합니다.

## 4. 코드에서 드러나는 팀의 작업 방식

문서화되지 않았지만 코드에 남아 있는 흔적들입니다. 이어받는 팀이 알아 두면 좋습니다.

- **주석이 "무엇"이 아니라 "왜"를 설명합니다.** 예:
  ```cpp
  // 드래그 중에는 히트 판정을 하지 않는다.
  // 빠르게 끌면 커서가 축 캡슐을 벗어나는데, 그때 eAxis가 NONE이 되면 드래그가 끊긴다.
  ```
  버그를 고친 뒤 그 이유를 주석으로 남기는 습관이 있습니다. 삭제하기 전에 한 번 읽어 보길 권합니다.
- **`// Todo:` 주석이 곧 백로그입니다.** `grep -rn "Todo" JungleTechLab_Week3/` 로 남은 작업을 볼 수 있습니다.
- **주석 처리된 옛 코드가 남아 있습니다.** 대부분 "원근/직교를 따로 처리하던 시절"의 코드로, 통합 투영으로 대체된 흔적입니다. 정리해도 무방합니다.
- **핵심 자료구조와 직렬화에는 단위 테스트가 있습니다** (`Test/UnitTest`). 렌더링/입력은 테스트가 없습니다.
